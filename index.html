Contracts & workflow
Phase 1 Lock a contract before starting — every engagement needs one
Board Demo Sprint USD 20–30K
Objective
2–3 working prototypes the GC can show the board
Acceptance
Artifacts run on real data. Not slides.
Non-goals
Production-grade code, security review
Done when
Client can screenshot and demo unassisted
Stop if: Champion loses interest mid-week. No one from client team is available to build. It becomes a vendor demo, not a collaborative build.
Champion Accelerator USD 50–70K
Objective
One production-adjacent tool + client's team can build the next one
Acceptance
Tool deployed in staging. Client's champion explains how it works.
Non-goals
Full production security review. Ongoing maintenance SLA.
Done when
Client's team ships next tool feature without LQ involvement
Stop if: Client can't dedicate a consistent lead for 6+ weeks. Tool hits a hard IT constraint that can't be worked around.
LQ Academy Cohort USD 5–15K / head
Objective
Credentialed lawyers who can vibe code at production-adjacent level
Acceptance
Each participant ships one working tool. Pass/fail on functionality.
Non-goals
Guaranteed hires. Long-term engagement.
Done when
Participant can explain their tool's architecture to an engineer
Stop if: Participant org won't let them share context. No time commitment from participants. Cohort below minimum size.
Every sprint ends with a handoff packet — this is the actual product
Step 1
Change summary
What was built and why. One paragraph the GC can paste into a board deck.
Step 2
File inventory
Exact files touched. Blast radius. What breaks if you delete it.
Step 3
Test evidence
Before/after. What was verified. What wasn't.
Step 4
Risk + rollback
What could go wrong in production. How to roll back in 2 commands.
LQ build rules — these apply to every engagement
No vibe coding auth. Review every line that touches authentication, tokens, or permissions.
Environment variables only. Never hardcode API keys, client names, or secrets in shipped code.
Max 500 lines per file. If a file grows beyond 500 lines, flag it for refactor (James C rule).
Error handling from day one. Every function has a defined failure mode before it goes to demo.
One feature = one change set. Don't mix behavior change with style cleanup in the same sprint.
Data never leaves the client's environment unless explicitly agreed and documented in the contract.
Before every sprint: run the PACT check
P
Problem framing
What specific workflow are you solving? What does "done" look like to the GC?
A
Acceptance design
Define one check that fails before and passes after. One guardrail that must stay green.
C
Change set
Surgical. One problem, one fix. Don't refactor adjacent code in the same sprint.
T
Trace + test
Show evidence. What was tested, what wasn't. Residual risk with explicit rationale.
